# Decisions — Should I Text Him?

Key engineering/product decisions and the reasoning behind them, so future iteration doesn't relitigate settled tradeoffs without cause.

## 1. Local deterministic judgment engine instead of a hosted AI model (v1)

**Decision:** `JudgmentEngine` is pure on-device Swift logic (keyword/pattern scoring), not a call to OpenAI, Anthropic, or any hosted model.

**Why:**
- The Day 1 spec is explicit: *"NEVER place an OpenAI API key or any secret inside the iOS app,"* and if no approved secure backend exists, either stand one up with clear documentation, or *"build the client abstraction and a deterministic local fallback so the app remains functional, and mark the server connection as an explicit release blocker."*
- This repository started empty — there is no existing approved backend/proxy pattern in this environment to reuse, and standing up a new one (hosting account, domain, billing, secret management) is a business/infrastructure decision outside what a single build session can responsibly make on the founder's behalf.
- The Factory doc's own default technical profile is "no backend by default," "AI should only be introduced when semantic understanding or generation materially improves the product," and "prefer low operating cost."
- A deterministic engine fully satisfies the product's actual job (fast gut-check verdict + templated rewrites) without incurring per-request AI cost, latency, an outage surface, or a privacy/security footprint — for a Day 1 experiment, that's a strictly better starting point, not a lesser one.
- This is **not** "faking" an AI connection — the UI never claims to call a model, and `API_CONTRACT.md`/`APP_STORE_METADATA.md` are written to avoid implying hosted-AI-backed judgment.

**Consequence:** the app makes zero network requests, needs zero secrets, and ships with a materially smaller security/privacy surface than a networked v1 would have. The upgrade path to a real backend is fully specified in `API_CONTRACT.md` for if/when usage data justifies the cost.

## 2. No accounts, no persistence, no analytics in v1

**Decision:** No login, no local database, no `UserDefaults` usage, no analytics SDK.

**Why:** Nothing in the product flow (paste → verdict → optional rewrite → copy/share) requires remembering anything across sessions. The Factory doc's default profile is "no account by default," "no tracking by default," "persist locally only when persistence materially improves the product." Skipping this layer also means `PrivacyInfo.xcprivacy` can honestly declare zero required-reason API usage and zero tracking, which simplifies both the privacy review and the App Store questionnaire.

## 3. No monetization in v1

**Decision:** Free, no IAP, no subscription.

**Why:** The Day 1 spec explicitly forbids a weekly subscription and says *"If monetization would slow the initial production release, leave the first version free and document the exact follow-up implementation."* Since there's no variable AI cost per use (decision #1), there's also no cost-recovery pressure forcing monetization on day one. See `POST_LAUNCH.md` for the specified one-time-unlock follow-up path using StoreKit 2.

## 4. Simple text-based share instead of a rendered image share card

**Decision:** `ShareLink` shares a plain-text string (verdict headline + app name), not a custom-rendered image card.

**Why:** The product requirement is "a privacy-safe result card" that excludes the original message by default — a text share satisfies that requirement completely. A rendered/branded image card (via `ImageRenderer`) would add polish and is a reasonable v1.1 candidate (tracked in `POST_LAUNCH.md`), but wasn't built now to keep the surface area small and because it could not be visually verified without Xcode in this environment (see "Environment constraint" below).

## 5. `objectVersion`/format of the hand-authored `.xcodeproj`

**Decision:** The Xcode project file was constructed programmatically (not by Xcode itself, since Xcode doesn't run outside macOS) at `objectVersion = 60`, matching a recent Xcode (16.x) project format, with a traditional group-based file structure (not the newer file-system-synchronized-group format) for maximum compatibility across recent Xcode versions.

**Why:** This container has no macOS/Xcode toolchain (see below), so the `.xcodeproj` could not be generated by Xcode's own "New Project" flow. It was hand-built to mirror exactly what that flow produces. If Xcode reports the project needs updating on first open, that is expected and safe to accept — see `RELEASE_CHECKLIST.md`.

## 6. Environment constraint: no Xcode/macOS/Swift toolchain in this build environment

**Fact, not a choice:** this session ran in a Linux container with no `swift`, `swiftc`, or `xcodebuild` available (Xcode is macOS-only). Every Swift file, the project file, and the test suite were written and manually reviewed for correctness but **could not be compiled, run, or tested by this session.**

**Consequence:** compiling, running the test suite, and all physical-device/simulator QA (VoiceOver, Dynamic Type, Reduce Motion, light/dark mode, relaunch, keyboard behavior) must happen on a Mac with Xcode before this app is submission-ready. This is the single largest item in `FOUNDER_ACTION_REQUIRED.md` and `RELEASE_CHECKLIST.md` — everything else in this repo is written to make that first build pass cleanly, but it has not been proven to compile.
