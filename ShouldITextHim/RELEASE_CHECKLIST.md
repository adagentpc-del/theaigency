## Status note (third repair — self-hosted local-inference architecture)

Two physical-device QA passes previously reshaped judgment (isolated-message defaulting to SEND IT too often, then keyword-based hostility detection missing plain profanity). This repair is a backend/architecture migration, not a new QA-found judgment defect: the semantic-judgment backend moved off a hosted third-party AI provider entirely, onto a **self-hosted local language model** (`RemoteAIJudgmentProvider` + `server/`, now a persistent Node/Express service calling a local inference server), and a fifth verdict (`NEED MORE CONTEXT`) was added so the model has an honest way to say it doesn't have enough information, instead of guessing. **The iOS side, like every prior repair, was authored in a Linux container with no Xcode/macOS toolchain and has not been compiled or test-run.** Unlike prior rounds, **this container does have Node available**, so the server side is materially better verified this round — see the table below for exactly what was and wasn't run for real.

## What changed in this repair

- **Backend migration**: `server/` no longer uses any hosted third-party AI provider. It's now a persistent Node/Express service (not serverless) that calls a self-hosted local language model via an OpenAI-compatible inference server (llama.cpp server or Ollama). See `server/README.md` for the architecture diagram and `DECISIONS.md` decisions 18–19.
- **Fifth verdict added**: `Verdict.needContext` / `RecommendedAction.addContext`, wired end-to-end (model prompt → schema → client validation → `VerdictView`'s new ADD MORE CONTEXT control → `JudgeViewModel.returnToAddContext()`). See `DECISIONS.md` decision 20.
- **The "absence of a problem is not evidence for send" rule is now explicit in the prompt**, not just implicit in the local-rule invariant: `send` requires affirmative evidence of appropriate tone, goal advancement, and context consistency.
- **New model benchmark harness**: `server/scripts/benchmark.ts` + `server/benchmark/fixtures.json` (the same 60 fixtures as the iOS test suite, in wire format), with a documented pass/fail threshold. See `DECISIONS.md` decision 21.
- **Real rate limiting**: `server/src/lib/rateLimiter.ts`, a genuine in-memory per-IP limiter — meaningful now that the server is a persistent process, unlike the previous serverless deployment where an in-memory counter would have been false confidence.
- **A hard production-safety guard**: the server refuses to start with `NODE_ENV=production` and a localhost/loopback `LOCAL_LLM_BASE_URL`, so a dev config can never accidentally ship as production.
- **Test suite** gained coverage for `need_context`/`add_context` in `RemoteAIJudgmentProviderTests.swift`, `AdversarialSemanticFixtureTests.swift`, and `JudgeViewModelTests.swift`.
- **Privacy/security posture**: what leaves the device is unchanged from the previous repair (still the proposed message/goal/context, still only when semantic judgment runs); who processes it changed from a third-party hosted-AI provider to theAIgincy's own self-hosted infrastructure. `PRIVACY_DATA_MAP.md` and `SECURITY_REVIEW.md` were both updated to describe this precisely.

## Recommended first steps

1. **Provision inference hardware and stand up a local inference server** (llama.cpp server or Ollama) — see `server/README.md`.
2. **Run the model benchmark** (`cd server && npm install && npm run benchmark -- --model <candidate>`) against every candidate model you're considering, and deploy only one that clears the documented threshold. Do not pick a model on speed or preference alone.
3. **Deploy `server/`** (Docker Compose or bare-metal, per `server/README.md`) with the winning model configured, then **update `RemoteAIJudgmentProvider.defaultEndpoint`** in the Swift source to the real deployed URL.
4. On a Mac: open `ShouldITextHim.xcodeproj` in current Xcode, build the `ShouldITextHim` scheme, fix any compiler errors.
5. Run the test suite (`Cmd+U`). Everything except `RemoteAIJudgmentProviderLiveTests` should run with no network/credentials needed. To also run the live suite, set `SHOULDITEXTHIM_LIVE_JUDGE_ENDPOINT` to your deployed URL on the test scheme and re-run — treat any failures there as real prompt/model-quality signal, not a test to loosen.
6. Run on a physical iPhone against the real deployed server. Walk the full 4-step flow with: the exact profanity regression case; a genuinely healthy message (calm apology, mutual flirting); a case with too little context (confirm NEED MORE CONTEXT and the ADD MORE CONTEXT button work); a safety-routed example; and — with the device in Airplane Mode — confirm the offline-fallback banner and retry button work.
7. Toggle VoiceOver, max Dynamic Type, and Reduce Motion and re-walk the flow.
8. Add real App Icon artwork (still outstanding from the first release).
9. Re-verify the App Store Privacy questionnaire against `PRIVACY_DATA_MAP.md` — the answers themselves are unchanged from the previous repair (User Content is still collected/transmitted), but re-confirm the App Review notes describe a self-hosted model, not a named third-party provider.
10. Once green, proceed to TestFlight per Apple's current process.
