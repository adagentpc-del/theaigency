# Start Me — Decisions Log

## Build environment has no Xcode/Swift toolchain

This build was produced in a Linux container with no `xcodebuild`, no
`swift` CLI, and no simulator. Every Swift file was hand-authored and
manually traced for syntactic and logical correctness (import statements,
type signatures, access control, SwiftUI API usage checked against known
iOS 17 SDK surface), and the `.xcodeproj` was generated by a small Python
script (not checked into the repo) that mirrors `ShouldITextHim.xcodeproj`'s
proven structure line-for-line, with structural self-checks (balanced
braces, every build-phase file reference resolves to a file that exists on
disk, target IDs consistent between the project file and the shared
scheme). None of this substitutes for an actual `xcodebuild` run. See
`docs/RELEASE_CHECKLIST.md` for exactly what remains unverified.

## Repo structure: added `apps/start-me/` without moving `ShouldITextHim/`

The task's suggested target structure nests every app under `apps/<slug>/`
with shared factory infrastructure under `/shared`. The actual repository
at session start had `ShouldITextHim/` living at the repo root (its own
`.xcodeproj`, docs, and a `server/` directory), with no `apps/` directory
and no root-level `README.md` or `MICRO_APP_FACTORY.md` yet.

Moving `ShouldITextHim/` into `apps/should-i-text-him/` would touch every
file path inside an app that already has its own feature branch
(`claude/should-i-text-him-app-sdztph`) and, per this task's own rules,
that branch must not be modified. Retroactively restructuring a sibling
app's paths is exactly the kind of unnecessary risk the brief warns
against ("Do not blindly move the existing project if doing so could break
paths"). So: `ShouldITextHim/` was left exactly where it was, and Start Me
was added cleanly at `apps/start-me/`. A root `README.md` was added (none
existed before) that indexes both apps by their real paths, and a root
`.gitignore` was added so every future app under `apps/` gets standard
Xcode ignores without needing its own copy. If/when the factory decides to
normalize `ShouldITextHim/` under `apps/`, that should be its own,
separately-reviewed change on its own branch.

## Classification: substring keyword router, not NLP

Section 11 of the brief explicitly asks for something "compact and
understandable," not a brittle keyword tree. `TaskStarterEngine.classify(_:)`
is an ordered list of (category, [keyword]) pairs, first match wins. This
is intentionally simple and has known, documented limitations (see
`docs/PRODUCT_QA.md` §"Known limitations") rather than trying to be a real
classifier. Two concrete fixes made during authoring, both caught by
building out the 79-fixture test suite before trusting the design:

- `"apartment"` was removed from the cleaning keyword list. It's needed
  nowhere (the spec's own `clean my entire apartment` example already
  matches via `"clean"`), and left in, it silently miscategorized any
  input that merely mentioned an apartment (e.g. "that whole thing with
  the apartment lease") as a cleaning task.
- The workout category's bare `" run "` keyword was replaced with the more
  specific `"for a run"` / `"go running"`. Bare `"run"` matched inside
  "run errands," incorrectly routing a shopping-trip errand to a workout
  starter action.

## General fallback: two shapes, not one

The brief's own two examples for unknown input pull in different
directions: `"finish the Johnson thing"` wants a dynamic "Open whatever
you need to work on X" sentence built from the user's words, while
`"I need to get my shit together"` (from the QA section) wants a plain,
generic tiny action ("Stand up and put one thing where it belongs.") — not
"Open whatever you need to work on the get my shit together," which is
what naively applying the first template to the second input would
produce.

The resolution: `TaskStarterEngine.fallbackObjectPhrase(from:)` only
returns a dynamic sentence when what's left after stripping lead-in verbs
("finish ", "I need to ", …) actually reads as a noun phrase — it starts
with an article or possessive ("the," "a," "my," …). "the Johnson thing"
qualifies; "get my shit together" doesn't (it still starts with a verb),
so it falls through to a generic library entry instead. This is a
principled, testable rule rather than a special case for one input — see
`TaskStarterEngineTests.test_unknownInputWithNounPhrase_producesDynamicFallback`
and the general-fallback fixtures in `StarterFixtures.swift`. The literal
wording "Stand up and put one thing where it belongs." from the QA example
was not hard-coded verbatim; the actual output satisfies the same
invariant (tiny, physical, non-planning) — documented honestly in
`docs/PRODUCT_QA.md` rather than silently claiming an exact match that
doesn't exist in the code.

## No recent-task history persisted

The brief allows keeping "a short, local, clearly removable" recent-task
history for UX if wanted, but doesn't require it. Start Me V1 stores no
task text at all — not even briefly beyond the current in-memory flow.
This is a stricter privacy stance than the minimum required, chosen
because it removes an entire category of privacy review, `PrivacyInfo.xcprivacy`
complexity, and "clearly removable" UI work for a feature (recent-task
autofill) that isn't part of the core loop. If usage data later shows
users want to re-run a recent task, see `docs/POST_LAUNCH.md`.

## Accent color: warm ember-orange, not purple

The brief explicitly warns against "purple AI branding" and "neon AI
aesthetics." `ShouldITextHim`'s accent color is purple/magenta (fitting its
dating-advice product). Start Me's accent
(`Assets.xcassets/AccentColor.colorset`) is a warm orange/ember
(`RGB(0.98, 0.33, 0.13)` light / a brighter variant in dark mode),
deliberately chosen to evoke "ignition/movement" per the icon direction in
`docs/APP_STORE_METADATA.md`, and to read as a distinct, non-generic
product identity from its sibling app.
